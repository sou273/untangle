# Untangle — 提出用の説明文（下書き）

> 第5回 Agentic AI Hackathon with Google Cloud 提出用。実装と数字はリポジトリの状態に合わせて更新する。

## ひとことで

**決裁者の判断を、テスト済みの「規程」として引き出し、共有知にするエージェント。**
小さな店の「これ、どうしますか？」のやり取りを送るだけで、エージェントが判断を場面として記録し、食い違いを見つけて決裁者に聞き返し、決裁者のルールでテストした規程に育てる。

## ユーザー像

- 個人店・零細企業の決裁者（店主・社長・マネージャー）。IT担当はいない
- その店で働くスタッフ（アルバイト・パート・事務員）

開発者自身が、切子体験工房の二代目マネージャーとして、この立場で毎日判断している。

## 課題

小さな店の判断は、決裁者の頭の中にしかない。

- スタッフは同じことを何度も聞きに来る。決裁者が不在だと止まる
- 記録に残るのは「何を決めたか」だけで、「なぜそう決めたか」は残らない
- 人が入れ替わると、判断の基準ごと消える（事業承継でも同じことが起きる）
- AIに任せようにも、どこまで任せてよいかの根拠が無い。「優秀なAIになんとなく任せる」と、誤りに誰も気づけない

実際に切子体験工房で団体予約の記録160件を見直すと、**学校団体の約4割で、生徒が大人として登録されていた**（同じ条件で判断が割れていた）。決裁者自身も、自分の判断が揺れていることに気づいていなかった。

## ソリューション

普段のやり取り（決裁者とスタッフのチャット、業務の中で人が直した跡）を送るだけで、次の流れが自動で回る。

1. **伏せる**: 名前・電話・日付などを、店の台帳・決まった規則・Gemma（このサービスの中だけで動く公開モデル）で伏せる。外部のGeminiには伏せた後の文しか渡さない。元の文は保存しない
2. **場面にする**: Geminiが、伏せた後の文から「状況・問い・判断・理由・判断者」を読み取る。判断は問いの選択肢から選ばせる
3. **聞き返す**: 引き継ぎエージェント（ADK）が巡回し、食い違い・初めての型・規程と違う判断・溜まった型を見つけて、決裁者に一言で答えられる質問を作る。分かっていることは聞かない
4. **テストする**: 決裁者が確定した条文を、過去の場面に当て直して一致を数える（数えるのはAIではなく決まったプログラム）
5. **完了を宣言する**: 4つの確認がそろったら「◯◯について、すべての解析が終わりました」と出し、規程の版を出す
   - 答えられない場面は残っていないか／答えはあなたと同じか／もう新しい話は出てこないか／あなたへの質問は残っていないか
6. **3つの出口で渡す**: スタッフ向けマニュアル／AIへの指示（テスト一式を同梱）／自動化の仕様書。AIに渡す前に、Geminiに規程だけを渡して同梱のテストを解かせ、合格したものだけを渡す

## 「固く渡す」— 自律性とガバナンスの両立

このハッカソンのテーマ「作れる」から「使える」へに対する答えは、**決裁者が決めたルールに則ってテストし、問題がなければ渡す**こと。

| 層 | 何を固くしているか |
|---|---|
| データ | AIに見せる範囲も決裁者の規程に含める。伏せる処理はAIに頼まず決まった規則＋自前のGemmaで行い、**伏せ方そのものもテストに合格してから使う**（消し漏れ0件・消しすぎ0件） |
| 判断 | いつ聞くかの判定は決まったプログラム。エージェントが変えられるのは質問の言い回しだけで、選択肢は変えられない |
| 権限 | エージェントには条文を確定・変更する道具も、質問に答える道具も渡していない（テストで固定）。確定できるのは決裁者の操作だけ |
| 合否 | 規程のテストも、AIへの指示のテストも、正解を数えるのはUntangle側の決まったプログラム。外れは「規則の外れ／読み取りの外れ／揺れ」に分けて数える |
| 出口 | AIへの指示は、規程にある選択肢から選ぶ形でしか答えられない。規程に無い場面は「決裁者に回します」と答えることもテストで確かめる |
| 可観測性 | エージェントが呼んだ道具・AIに渡した内容（用途と文字数）をすべて記録し、画面に出す |

## 実測（デモ用の架空データ）

- 規程から作った「AIへの指示」を gemini-3.5-flash に渡したテスト: 通常の場面 **130件中130件で正解**、規程に無い場面 **2件中2件で「決裁者に回します」**
  - 答えを自由記述にしていたときは、130件中15件で日本語が崩れた（条文番号は正しかった）。選択肢から選ばせる形にして解消
- 伏せ方のテスト（店の台帳が空の、最も厳しい条件）: 調整に使っていない確認用20文で、AIに届いた名前 **27語中1語**（1文字の店名）・消しすぎ0 → **不合格**。取引先の台帳を辞書に加えると **0語で合格**
- 隠れた条件の発見: 居酒屋の「土曜8名を断った・受けた」の揺れに、店主が「2回転目の予約があるかどうか」と一言答えると、記録にある項目から判断を分ける条件を見つけ、条文を2つに分けて過去の場面で合格させる

## どの業態でも

接続の仕組みではなく「判断」を扱うので、業態を問わない。デモでは性格の違う2つの店を同じ仕組みで扱う。

- 切子体験工房: 過去1年の記録160件があり、規程も一部ある。団体予約の人数の数え方
- 居酒屋 とり松（架空）: 記録も規程も無いところから、店主の一言メモとアルバイトとのやり取りで溜めていく。予約の受け方

## 使っている Google Cloud

| 用途 | プロダクト |
|---|---|
| 画面・API・エージェント | **Cloud Run**（東京リージョン、専用サービスアカウントは Vertex AI の利用権限だけ） |
| 伏せる層の固有名詞検出 | **Gemma**（gemma3:4b、非公開の Cloud Run・CPU。呼べるのは本体のサービスアカウントだけ） |
| 場面の読み取り・質問の言い回し・AIへの指示のテスト | **Gemini API**（Vertex AI、gemini-3.5-flash、東京リージョン） |
| 引き継ぎエージェント | **Agent Development Kit (ADK)** |
| ビルドとイメージ | Cloud Build / Artifact Registry |

## これから

- 店の台帳（スタッフ名簿・取引先一覧）を取り込み、伏せ方のテストを店ごとに合格させてから使う
- Slack・LINE・Googleフォーム（スプレッドシート）からの自動の取り込み
- 規程を保存（Firestore）し、新しい場面で外れが増えたら規程の見直しを提案する（見守り）
- 「AIへの指示」の出口から、実績に応じて任せる範囲を段階的に広げる（見学 → 案 → 事後確認 → 自動）
